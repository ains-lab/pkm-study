# AI 세컨드 브레인 구축하기: Zotero, NotebookLM, LLM Wiki, Obsidian, Understand Anything을 연결한 개인 지식관리 시스템

## 1. 왜 새로운 세컨드 브레인이 필요한가
정보 과잉 시대의 지식 관리는 단순한 '수집(Collection)'을 넘어 '지식 증분(Knowledge Incrementation)'의 관점으로 전환되어야 한다. 대다수 사용자가 겪는 AI 대화의 한계는 세션이 종료됨과 동시에 맥락과 기억이 휘발된다는 점이다. 이는 지식이 사용자의 장기 기억 체계로 편입되는 것을 방해한다.

본 시스템 설계의 4대 핵심 목표는 다음과 같다.
*   **원본 보존 (Integrity)**: 가공되지 않은 소스의 무결성을 유지하여 언제든 근거로 회귀할 수 있도록 한다.
*   **출처 추적 (Provenance)**: 모든 합성된 지식에 대해 로컬 원본 경로와 서비스별 source ID를 명시한다.
*   **지식 증분 (Incrementality)**: AI와의 상호작용 결과를 기존 지식 카드에 누적하여 밀도를 높인다.
*   **관계 탐색 (Discovery)**: 파편화된 데이터 간의 구조적 관계를 시각화하여 연구 공백을 발견한다.

특히 NotebookLM과 같은 소스 기반 AI를 활용할 때는 '외부 지식(LLM Wiki)'과 '사용자의 고유 생각(My Notes)'을 엄격히 분리 설계해야 한다. 이는 외부 정보의 오염으로부터 개인의 통찰을 보호하고, 동시에 방대한 외부 지식을 효율적으로 소화하기 위한 필수 전제 조건이다.

## 2. 전체 아키텍처 한눈에 보기
본 시스템은 데이터가 수집되어 정제된 지식으로 승격되고, 다시 새로운 질문을 유도하는 환류(Feedback) 파이프라인을 구축한다.

### 지식 관리 데이터 흐름 (Data Flow)
```text
[원본 계층: Raw] 웹·논문·영상 → Zotero (서지정보 & SHA-256 해시 보존)
    ↓
[분석 계층: Analysis] Zotero/raw → NotebookLM (특정 소스 묶음 집중 질의)
    ↓
[지식 계층: Long-term] LLM Wiki → Obsidian (정규화된 Markdown 지식 인터페이스)
    ↓
[탐색 계층: Discovery] Understand Anything / Graphify (지식 그래프 & 공백 탐색)
    ↓
[환류 계층: Feedback] 발견된 모순/공백 → NotebookLM·Wiki 재입력 및 지식 보충
```

### 계층 분리 원칙
1.  **원본 계층(Raw Layer)**: 수정 불가능한 원천 데이터와 메타데이터 보관.
2.  **분석 계층(Analysis Layer)**: 특정 연구 주제에 대해 AI와 대화하며 도출한 임시 합성물.
3.  **장기 지식 계층(Long-term Knowledge Layer)**: 검토를 거쳐 정규화된, 재사용 가능한 지식 카드.

## 3. 도구별 역할과 책임 (Separation of Concerns)
시스템의 지속 가능성을 위해 각 도구가 담당하는 기술적 경계를 명확히 정의한다.

| 도구 | 중심 대상 | 역할 및 책임 | 적합한 질문/작업 |
| :--- | :--- | :--- | :--- |
| **Zotero & Zotero MCP** | 원본/서지정보 | 서지 레코드, 첨부 파일과 원문을 구분해 보존하고 에이전트가 검색할 수 있도록 연결한다. | "이 논문의 부모 메타데이터와 원문 PDF를 구분해 가져와라." |
| **NotebookLM & notebooklm-py** | 특정 소스 묶음 | **연구 작업실**. 특정 컨텍스트 내에서의 집중 질의, 요약, 비교 보고서 생성. | "선택한 5개의 소스를 바탕으로 기술적 모순점을 분석하라." |
| **LLM Wiki (Obsidian)** | Markdown 지식 | **지식 저장소 및 인터페이스**. 인간과 에이전트가 공통으로 이해하는 영구 지식 카드 보관. | "현재까지 축적된 'AI 지식 워크플로'에 대한 핵심 정의를 보여달라." |
| **Graphify** | 코드·문서·미디어 | **관계 경로 분석기**. 이질적인 소스 간의 연결 경로와 신뢰도(EXTRACTED/INFERRED) 분석. | "개념 A와 기술 B 사이의 논리적 연결 경로는 무엇인가?" |
| **Understand Anything** | 위키·문서 전체 | **시각적 대시보드**. 지식 군집과 관계, 고립 노드 및 가이드 투어를 통한 구조적 탐색. | "지식 베이스의 전체적인 군집 구조와 고립된 노드는 무엇인가?" |
| **CodeGraph** | 로컬 코드베이스 | **심볼 영향 분석기**. 코드 심볼, 호출 계층, 변경에 따른 영향 범위(Blast Radius) 추적. | "이 함수를 수정할 때 영향을 받는 상위 모듈은 무엇인가?" |

## 4. 프로젝트 디렉터리 설계
에이전트가 시스템 아키텍처를 즉시 파악할 수 있도록 표준화된 폴더 구조를 강제한다.

```markdown
/Project-Root
├── SCHEMA.md          # 데이터 규격, 태크 Taxonomy, SHA-256 체크 로직 정의
├── index.md           # 전체 지식 지도 및 주요 쿼리 인덱스 (MOC)
├── log.md             # 시스템 업데이트 기록 및 에이전트 작업 히스토리
├── raw/               # Zotero에서 인제스트된 원본 Markdown 및 PDF (Read-only)
├── entities/          # 도구, 인물, 조직 등 고유 개체 문서
├── concepts/          # 기술 원리, 방법론, 이론 문서
├── comparisons/       # 도구/기술 간 비교 및 벤치마킹 문서
├── queries/           # NotebookLM 답변을 정규화한 Canonical Query 문서
└── .ua/               # Understand Anything 설정 및 지식 그래프 캐시
```

## 5. LLM Wiki 스키마 설계
에이전트와 사람이 데이터의 정합성을 동시에 검증할 수 있도록 Frontmatter 규격을 정의한다.

*   **Frontmatter 필드**:
    *   `title`: 문서의 정규 명칭.
    *   `tags`: Taxonomy에 근거한 계층적 태그 (예: #workflow/research).
    *   `sources`: 근거가 된 로컬 `raw/` 파일 경로.
    *   `confidence`: 지식 신뢰 등급 (High/Medium/Low).
    *   `contested`: 내용 중 논란이나 모순 존재 여부 (Boolean).
    *   `notebooklm_source_id`: NotebookLM source와 로컬 원본을 연결할 때 사용하는 선택적 식별자.

*   **Taxonomy 원칙**: 페이지 생성은 반드시 근거(Provenance)가 확보된 시점에 수행하며, 출처가 불분명한 정보는 `confidence: Low`로 마킹하여 관리한다.

## 6. 1단계: 원본 자료 수집과 보존
모든 지식의 무결성은 원본의 상태 관리에서 시작된다.
1.  **Zotero 수집**: Zotero 커넥터를 활용하여 웹, 논문, 영상의 메타데이터를 누락 없이 확보한다.
2.  **SHA-256 기반 Drift 방지**: 수집된 자료를 `raw/` 폴더로 인제스트할 때 `SHA-256` 해시를 생성한다. 이는 에이전트가 정보를 읽을 때 원본이 변조되거나 유실되는 'Source Drift' 현상을 감지하기 위함이다.
3.  **중복 체크**: 동일한 DOI나 URL을 가진 자료의 중복 수집을 방지하는 체크리스트를 가동하여 지식베이스의 노이즈를 최소화한다.

## 7. 2단계: NotebookLM 노트북 구성
방대한 데이터 중 특정 연구 목적에 부합하는 자료만 선별하여 컨텍스트 윈도우의 효율을 극대화한다.
*   **연구 단위 설정**: 주제와 무관한 소스를 제거하고, 텍스트 추출이 불가능한 이미지는 OCR 처리를 거쳐 소스 상태를 검증(Source Validation)한다.
*   **완전 중복 제거**: 의미적으로 100% 일치하는 문서를 제거하여 AI의 주의력 분산을 방지한다.

## 8. 3단계: NotebookLM에서 질문하고 검증하기
AI 답변의 신뢰도를 기술적으로 검증하는 프로세스를 수행한다.
*   **구조적 질의**: `notebooklm ask --notebook <notebook-id> --json "질문"` 명령을 통해 답변과 인용 정보를 JSON 형식으로 확보한다.
*   **Source ID 매핑**: 답변의 `references[].source_id`를 로컬 Markdown frontmatter의 `notebooklm_source_id`와 대조하여 실제 원본 파일과의 정합성을 확인한다. 매핑되지 않는 인용은 추정하지 않고 `partial` 또는 `unavailable` 상태로 관리한다.

## 9. 4단계: 재사용 가능한 답변만 queries/에 편입
정보 과잉을 방지하기 위한 엄격한 필터링 정책(Filter Policy)을 적용한다.
*   **저장 가치 판정**: 
    1. 복수의 소스를 결합하여 새로운 인사이트를 도출했는가?
    2. 기존 위키 문서 간의 새로운 관계를 정의하는가?
    3. 반복 사용 가능한 의사결정 로직을 포함하는가?
*   **Canonical Query 정책**: 단순 Q&A 대화 기록은 저장하지 않는다. 대신 해당 질문에 대한 최종 정규 답변인 `canonical query` 문서를 생성하거나 기존 문서를 갱신하여 지식을 증분시킨다.

## 10. 5단계: LLM Wiki 문서 생성
분석 결과를 영구 지식으로 승격시키는 자동화 절차를 수행한다.
*   **중복 방지 및 역링크**: 신규 문서 생성 전 기존 `entities/`, `concepts/`를 검색하여 중복을 피하고, 관련 문서 간의 역링크(Backlink)를 자동으로 설정한다.
*   **자동 로그**: `index.md`의 통계와 `log.md`의 작업 기록을 즉시 업데이트하여 시스템 가시성을 확보한다.

## 11. 6단계: Wiki Lint 품질 검증
지식베이스의 무결성을 유지하기 위해 다음 10가지 린트 항목을 주기적으로 점검한다.

| 점검 항목 | 기술적 지표 및 원칙 |
| :--- | :--- |
| **Broken Links** | 위키링크가 실제 목적지 파일을 가리키는지 확인. |
| **Orphan Notes** | 연결된 링크가 없는 고립 문서 탐색. |
| **SHA Drift** | `raw/` 원본의 해시값 변동 여부 확인. |
| **Confidence Score** | 신뢰도가 Low인 문서의 재검토 기한 확인. |
| **Provenance Integrity** | `sources` 필드의 로컬 경로와 선택적 source ID 매핑이 유효한지 확인. |
| **Wikilink Density** | **최소 2개 이상의 유효한 위키링크** 존재 여부 확인. |
| **Atomic Size** | **200줄 이상의 문서는 분할** 원칙 준수 여부 점검. |
| **Metadata Drift** | 필수 Frontmatter 필드 누락 여부. |
| **Tag Taxonomy** | 정의되지 않은 비표준 태그 사용 여부. |
| **Contested Resolve** | 모순(Contested) 마킹된 항목의 해결 상태 확인. |

## 12. 7단계: UA 지식그래프 생성
텍스트 기반 지식을 구조적 데이터로 변환하여 시각화한다.
*   **명령어 전략**: 코드베이스 구조 분석용 `understand`와 Karpathy 패턴 위키 분석용 `understand-knowledge`를 구분하여 실행한다.
*   **관계 모델**: `article`, `entity`, `topic`, `claim`, `source` 노드 간의 다층적 관계를 구축하여 논리적 계층을 시각화한다.

## 13. 8단계: 지식그래프에서 통찰 발견
그래프 이론을 적용하여 시스템 내의 지식 구조를 진단한다.
*   **진단 항목**:
    *   **중심 노드(Hub)**: 지식이 집중되는 핵심 개념 식별.
    *   **브리지(Bridge)**: 서로 다른 도메인을 연결하는 매개 지식 발견.
    *   **고립 노드(Island)**: 시스템에 통합되지 못한 파편화된 정보 식별.
*   **해석 원칙**: 그래프상의 공백이 반드시 실제 지식의 부재를 의미하지 않으므로, 데이터 수집의 문제인지 실제 연구의 공백인지 비판적으로 해석하라.

## 14. 9단계: 그래프 통찰을 NotebookLM으로 다시 전달
발견된 공백과 모순을 메우기 위한 환류(Feedback) 공정을 완성한다.
*   **비판적 질의**: 그래프 분석을 통해 발견된 '증거 부족 주장(Claim)'이나 '논리적 모순 노드'를 NotebookLM에 입력하여 비판적 재질의를 수행한다. 이 과정을 통해 지식의 밀도를 높이고 논리적 허점을 보완한다.

## 15. 증분 동기화 전략
로컬 위키와 NotebookLM 간의 정합성을 위한 정규화 로직을 수행한다.
*   **의미적 정규화(Normalization)**: AI 가독성을 위해 헤더 레벨 조정, 코드 블록 태그 표준화, 특수 기호 이스케이프 처리를 수행하여 형식 차이에 의한 오독을 방지한다.
*   **교체 알고리즘**: 컨텍스트 윈도우 제한을 고려하여, 신뢰도가 낮거나 오래된 소스를 신규 고품질 소스로 점진적으로 교체하는 로직을 적용한다.

## 16. 실제 구축 결과 예시 (Snapshot)
시스템 가동 후 특정 시점에서 얻은 데이터 통계의 예시는 다음과 같다.
*   **통계**: `article: 20, entity: 8, claim: 20, topic: 4, source: 13`.
*   **구조**: 전체 노드 65개, 엣지(Edge) 184개, 레이어 5단계, 가이드 투어 4개.
*(본 수치는 특정 시점의 스냅샷이며 연구 진행도에 따라 변동됨)*

## 17. 운영 중 발견한 문제와 해결책
*   **중복 노드 문제**: `raw/`와 `wiki/`에 동일 명칭의 노드가 생성될 경우, 출처 기반 ID를 부여하여 명시적으로 관계를 정의하라.
*   **해시 불일치**: Markdown 변환 환경 차이로 해시가 변할 경우, 공백과 특수문자를 제거한 '의미적 텍스트 해시'를 대안으로 사용한다.
*   **AI 기능 오해**: AI가 도구의 최신 기능을 잘못 설명할 경우, 해당 도구의 `--help` 결과물을 최우선 소스로 입력하여 교정한다.

## 18. 보안과 개인정보 보호
*   **업로드 제한**: 기밀 문서, PII(개인 식별 정보), 보안 키는 외부 AI 클라우드 업로드 대상에서 엄격히 제외한다.
*   **무시 설정**: `.gitignore`와 `.ua/.understandignore`를 활용하여 인증 정보, 편집기 상태와 생성 산출물이 분석·공유 대상에 섞이지 않도록 한다.

## 19. 자동화 가능한 부분과 사람이 검토해야 할 부분
AI의 효율성과 인간의 비판적 사고를 최적으로 배분한다.

| 자동화 (Agent) | 인간 검토 (Human) |
| :--- | :--- |
| 자료 수집, 서지 정보 추출, 해시 생성 | 지식의 가치 판단 및 영구 저장 승인 |
| 초기 요약, 초안 생성, 형식 정규화 | 논리적 모순 확인 및 문맥적 보완 |
| 린트(Lint) 수행 및 깨진 링크 탐색 | 그래프 분석을 통한 연구 방향 결정 |
| 지식 그래프 노드 및 엣지 자동 생성 | 최종 인사이트 도출 및 비판적 환류 승인 |

## 20. 마무리: 도구가 아니라 지식 순환 시스템 만들기
본 시스템의 궁극적인 자산은 특정 유료 서비스가 아닌 로컬의 **Markdown 문서**와 그들 사이의 **출처 관계(Provenance)**이다. 도구는 기술 발전에 따라 언제든 교체될 수 있으나, 정밀하게 설계된 지식 아키텍처는 개인의 영구적인 지적 자산으로 남을 것이다.

### 부록

**A. 설치 및 사전 준비**
*   Python과 Node.js 환경을 준비하고 사용하는 도구의 공식 설치 문서를 확인한다.
*   Zotero와 필요한 MCP 플러그인을 설치한 뒤 부모 서지 레코드와 첨부 파일을 구분해 가져올 수 있는지 확인한다.
*   NotebookLM CLI는 `notebooklm auth check --test --json`으로 실제 인증 상태를 검증한다.
*   Obsidian에서 프로젝트 루트를 Vault로 열고 위키링크와 frontmatter가 정상 인식되는지 확인한다.
*   Understand Anything을 설치하고 위키 루트에서 `understand-knowledge`를 실행할 수 있는지 확인한다.

**B. 주요 명령어 모음**
*   **NotebookLM 인증**: `notebooklm auth check --test --json`
*   **Source 조회**: `notebooklm source list --notebook <notebook-id> --json`
*   **인용 포함 질의**: `notebooklm ask --notebook <notebook-id> --json "질문 내용"`
*   **위키 지식그래프 생성**: `$understand-anything:understand-knowledge`
*   **그래프 대시보드 실행**: `$understand-anything:understand-dashboard`

**C. 운영 체크리스트**
*   **일간(Collect)**: Zotero 커넥터로 신규 소스 수집 및 `raw/` 무결성 체크.
*   **주간(Compile)**: NotebookLM 질의를 통해 가치 있는 지식을 `queries/`로 승격.
*   **월간(Audit)**: 지식 그래프 분석을 통한 연구 공백 식별 및 10대 린트(Lint) 수행.
